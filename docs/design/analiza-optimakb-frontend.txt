SUMMARY: optimaKB frontend to SPA w React 18.3 + Vite 8 (`vite.config.js`: plugin-react, `base: './'`, build do `dist/dashboard`), bez routera, bez state managera, bez TypeScriptu i bez testów UI — jedyne zależności runtime to `react`, `react-dom` i `lucide-react`. Wejście: `index.html` (montuje `/src/main.jsx`, fonty z Google Fonts) → `main.jsx` opakowuje `<App/>` w `ErrorBoundary`. `App.jsx` trzyma tablicę `TABS` (11 stron, wszystkie `React.lazy` + `Suspense`), routing oparty wyłącznie o `window.location.hash` (`tabFromHash()`, `history.replaceState`, listener `hashchange`, syntetyczny stan `__notfound__` dla ekranu 404). Nawigacja jest pogrupowana w trzy kategorie (Operacje / Treść / Administracja), ma skróty Ctrl+1..9, `/` (focus na pierwszym `.search`), `?` (modal skrótów) oraz badge z liczbą pending draftów w Inboxie. App pobiera raz `/api/status` (`loadOverview`), zapisuje CSRF token z `payload.service.csrfToken` do modułowej zmiennej w `constants.js` i przekazuje cały payload jako prop `overview` do każdej strony; opcjonalny auto-refresh co 15 s odświeża wyłącznie `/api/status`. Warstwa HTTP to jedna funkcja `apiFetch()` w `constants.js`: prefiks `BASE_PATH` (`/panel` gdy pathname zawiera `/panel`), timeout 45 s przez `AbortController` + `AbortSignal.any`, automatyczny nagłówek `X-ERP-KB-CSRF` dla metod mutujących. Nad tym siedzi minimalny hook `useApi(path)` (data/loading/error/reload, opcjonalny polling — nigdzie nieużywany) oraz nieużywany `useMutation`. Bramkowanie treści (`shared/appContentGate.js`) NIE dotyczy ról — to jednolinijkowa reguła „które zakładki mogą się wyrenderować zanim przyjdzie payload `/api/status`” (tylko `overview` jest zależny). Bramkowanie rolowe jest realizowane ad hoc w komponentach przez `overview.service.role === 'admin'` (ukrywanie/disable przycisków w SourcesPage, AutomationPage), a realnie egzekwowane po stronie backendu (`erp_kb_dashboard_server.mjs`: role admin/operator/viewer, 403 `admin_required`, blokada mutacji dla viewera, walidacja CSRF). Globalny status to pasek `GlobalStatus.jsx` (Quality Gate, Freshness, Pending, Running, KB sync z tooltipem różnic registry/bundle/routing, KB set, last action) plus czysta funkcja `buildHealthCockpit(overview)` w `shared/healthCockpit.js`, która normalizuje statusy do OK/WARN/FAIL i liczy 7 sygnałów (quality, freshness, inbox, actions, sources, automation, mcp) + `overallStatus` = najgorszy z nich. Panel obsługuje pełny cykl życia wiedzy: ingest (AddDraftPage: URL/tekst/plik → `/api/drafts/analyze` → `/api/drafts`), review i promocję (InboxPage z bulk-preflight i pollingiem akcji), odkrywanie źródeł (SourcesPage: monitory + discovery candidates + triage + polityka półautomatu), automatyzację LLM (AutomationPage: shadow/canary/promotion gate/rollback/klucze providerów), uczenie (LearningPage — luki wiedzy; TrendsPage — metryki w czasie), raporty jakości z akcjami naprawczymi (ReportsPage), administrację MCP i kluczy API (McpPage) oraz podgląd systemu/akcji/crona (SystemPage). Frontend woła ~40 unikalnych endpointów REST pod `/api/*`, wszystkie zwracające JSON z konwencją `{ ok, message|error, actionId, ... }`. Długie operacje są asynchroniczne: endpoint zwraca `actionId`, a UI odpytuje `/api/actions/{id}` w pętli (120 prób × 2 s) do statusu FINISH/FAIL. Stylowanie to ręczny CSS (`styles.css` + 16 plików w `src/styles/`) z tokenami CSS i przełącznikiem motywu light/dark/system w `localStorage`.

REUSABLE:
  • Jeden punkt wejścia HTTP (apiFetch) z automatycznym prefiksem base path, wbudowanym timeoutem (AbortController + AbortSignal.any łączący sygnał zewnętrzny z timeoutowym) i automatycznym nagłówkiem CSRF wyłącznie dla metod mutujących — to warto przenieść 1:1, dokładając retry/backoff i jednolite parsowanie błędu.
  • Kontrakt API { ok, message|error, actionId } + jeden helper do wyciągania komunikatu błędu — spójna obsługa błędów w całej aplikacji bez try/catch-owego chaosu (w nowym projekcie: wynieść to do funkcji `unwrap(response)` zamiast powtarzać w każdym handlerze).
  • Wzorzec 'akcja asynchroniczna z actionId + polling statusu': endpoint mutujący zwraca actionId, UI odpytuje /api/actions/{id} do FINISH/FAIL i pokazuje status na żywo. Świetny dla długich buildów KB — w nowym projekcie zamienić polling na SSE/WebSocket albo przynajmniej wyekstrahować jeden hook `useActionPolling(actionId)`.
  • Dwufazowy bulk z preflightem: pierwszy request z { dryRun: true } zwraca preflightByNamespace z listą checków, UI pokazuje modal potwierdzenia, drugi request wykonuje operację. Bardzo dobry wzorzec bezpieczeństwa dla operacji nieodwracalnych.

  • Wizard ingestu z auto-analizą: jeden formularz obsługuje URL/tekst/plik, krok 'analyze' zwraca zaproponowany namespace KB, tytuł, tagi i treść wraz z informacją, który provider je dostarczył (providers.content/metadata + analysisConfidence) i z listą ostrzeżeń — użytkownik tylko koryguje.
  • Wskaźniki gotowości integracji jako pierwszorzędny element UI (KAG Readiness / DraftAnalyzeBadge: LLM, Tavily, Firecrawl, Exa, autopilot, freeze) — od razu widać, czego brakuje w konfiguracji, zamiast cichych awarii.
  • SafeExternalLink + safeExternalHref: whitelist protokołów http/https dla linków pochodzących z danych zewnętrznych (kandydaci discovery) — obrona przed javascript:/data: URL.
  • ThemeToggle light/dark/system oparty o data-theme na <html> i zmienne CSS, z zapamiętaniem w localStorage i domyślnym trybem systemowym.

WEAKNESSES:
  • Brak routera — routing na gołym window.location.hash z ręcznym history.replaceState. Nie ma prawdziwej historii (back/forward nie przełącza zakładek świadomie, bo używany jest replaceState), nie ma zagnieżdżonych tras ani parametrów ścieżki; parametry Inboxa są ręcznie sklejane w query string wewnątrz hasha. W nowym projekcie: react-router (lub TanStack Router) + typowane search params.
  • Brak warstwy cache/dedup zapytań. Każda strona woła własne useApi bez współdzielenia; /api/kbs jest pobierane oddzielnie przez KbPage i InboxPage, /api/automation/autopilot przez Overview, SourcesPage i AutomationPage, /api/automation/learning przez Overview i AutomationPage. Do tego przy każdym przełączeniu zakładki wszystko ładuje się od nowa. Docelowo: TanStack Query (cache, dedup, invalidacja, retry, stale-while-revalidate).
  • Prop drilling całego payloadu /api/status jako `overview` do każdej strony — strony sięgają po overview.service.role, overview.kbs, overview.actions, overview.automation..., co tworzy niejawną zależność od kształtu jednego wielkiego obiektu. Brak kontekstu/store i brak typów sprawia, że każda zmiana kontraktu backendu wykrywana jest dopiero w runtime (stąd wszechobecne `?.` i `|| []`).
  • Auto-refresh w App odświeża tylko /api/status — dane stron (inbox, akcje, discovery, MCP) się nie odświeżają, więc pasek GlobalStatus może pokazywać inny stan niż tabela pod nim. Jednocześnie useApi ma zaimplementowany autoRefresh, z którego nikt nie korzysta (martwa funkcjonalność).
  • Polling akcji zaimplementowany dwukrotnie (InboxPage.pollAction i ReportsPage.pollAction), z różną jakością: ReportsPage tworzy mountedRef = useRef(true) i NIGDY nie ustawia go na false przy odmontowaniu (brak useEffect z cleanupem), więc pętla 120×2 s żyje po opuszczeniu zakładki i wykonuje setState na odmontowanym komponencie. Powinien być jeden hook z AbortControllerem, backoffem i limitem czasu.
  • Polling zamiast strumienia zdarzeń: 4-minutowe pętle co 2 s na /api/actions/{id} oraz brak SSE/WebSocket dla postępu buildów. Przy kilku równoległych operacjach generuje to sporo zbędnego ruchu i i tak kończy się komunikatem 'sprawdź zakładkę System'.
  • Bulk reject w InboxPage odpala N równoległych requestów przez Promise.allSettled zamiast jednego endpointu bulk (podczas gdy bulk-promote-export istnieje) — brak atomowości, brak preflightu i ryzyko zalania serwera przy zaznaczeniu 50 pozycji. Podobnie 'Ponów wszystkie' w SystemPage robi sekwencyjną pętlę POST /api/actions/{id}/retry bez limitu współbieżności i bez możliwości anulowania.
  • Bramkowanie rolowe jest rozsiane po komponentach jako powtarzane `overview?.service?.role !== 'admin'` w propsie disabled (AutomationPage powtarza to ~8 razy) — brak jednego helpera typu can(action) / <RequireRole>. Efekt: łatwo zapomnieć bramki (np. widoczne pola kluczy API), a zakładki mcp/system są w całości dostępne dla każdej roli, mimo że backend i tak zwróci 403 — użytkownik dowiaduje się o braku uprawnień dopiero z błędu.
  • Nazwa appContentGate wprowadza w błąd — sugeruje bramkowanie treści, a realizuje jednoelementowy Set zakładek zależnych od payloadu overview. W praktyce jest to 5-linijkowy moduł z własnym plikiem testowym; w nowym projekcie zastąpiłbym to deklaratywnym `requiresStatus: true` w definicji trasy.
  • Martwy/nieużywany kod: useMutation.js (zdefiniowany, zero importów), ApiErrorBox.jsx (zdefiniowany, zero użyć — strony renderują surowe divy .formMessage), usePagination z Pagination.jsx (nieużywany), nieużyte importy (useRef w LearningPage, useEffect w TrendsPage, prop `overview` w TrendsPage, `data: _initialData` w LearningPage, `_overview` w InboxPage).
  • Niespójny sposób obsługi błędów i komunikatów: jedne strony używają useApi(error) + EmptyState, inne lokalnego stanu message/setMessage z surowym stringiem, jeszcze inne alert()/confirm()/prompt() z przeglądarki (SourcesPage: window.confirm przy usuwaniu źródła i bulk, window.prompt na nazwę widoku; McpPage: confirm przy usuwaniu użytkownika/klucza/serwera; LearningPage: alert po imporcie learning state). Brak systemu toastów i brak spójnego komponentu potwierdzenia.
  • Gigantyczne komponenty: SourcesPage 882 linie, McpPage 585, InboxPage 584, AutomationPage 400 — każdy z kilkunastoma useState (SourcesPage ma ~20), logiką sieciową, filtrowaniem i definicjami kolumn w jednym pliku. Brak podziału na kontener/prezentację i brak wydzielonych hooków domenowych (useDiscoveryCandidates, useSources, useMcpServers).
  • Zero testów frontendowych na poziomie komponentów (brak Vitest/RTL/Playwright). Testowane są tylko cztery czyste funkcje pomocnicze przez node:test w scripts/. Krytyczne przepływy (promocja draftu, bulk preflight, triage kandydatów, rotacja kluczy) nie mają żadnego pokrycia.
  • Brak TypeScriptu i brak jakiejkolwiek walidacji odpowiedzi (np. zod) przy bardzo bogatych, zagnieżdżonych payloadach (overview.discovery.semiAuto.metrics.falsePositiveRate itd.) — kod jest usiany defensywnym `?.`/`|| 0`, a literówka w polu manifestuje się jako ciche '—' zamiast błędu.
  • Ręcznie rysowane wykresy SVG (Overview health chart, TrendsPage linePath, DonutChart, BarChart) bez osi, siatki, tooltipów i obsługi pustych/jednopunktowych serii; Overview liczy `pts[pts.length-1]` bez zabezpieczenia, a TrendsPage pomija namespace'y z mniej niż 2 punktami. Warto użyć biblioteki (Recharts/visx) albo wydzielić jeden porządny komponent wykresu.
  • Logika biznesowa liczona na kliencie z danych `overview.actions`: 7-dniowa historia health, deduplikacja nieudanych akcji, ranking typów akcji — wyniki zależą od tego, ile akcji backend akurat zwrócił w /api/status (brak paginacji/zakresu czasu), więc wykres 'ostatnie 7 dni' może być nieprawdziwy. To powinien liczyć backend.
  • Hardkodowana lista ALL_KB_NAMESPACES (14 pozycji) w shared/mcp/kbConstants.js duplikuje dane, które backend już zwraca w /api/kbs — przy dodaniu KB trzeba pamiętać o edycji frontendu. Dodatkowo AddMcpKbSection wyświetla hardkodowane '{selectedCount} / 12 KB wybrane', co nie zgadza się z 14 namespace'ami w liście.
  • Kontrolowane inputy z wartościami undefined: initial state formularza w SourcesPage nie zawiera pól sourceRoot/basketRoot/filePatterns (są dodawane dopiero w resetForm/editSource), więc po otwarciu formularza typu 'directory' React dostaje value={undefined} → ostrzeżenie o przejściu z niekontrolowanego na kontrolowany.
  • Dostępność i UX szczegóły: DataTable używa `row.id || row.namespace || row.key || row.exportDir` jako klucza (dla wierszy bez żadnego z tych pól klucz to undefined — np. rebuildLog w ReportsPage i wiersze learningPenalties), część list używa indeksu jako klucza (alerty w TrendsPage, recentActions autopilota), a IconButton bez showLabel polega wyłącznie na tooltipie. Brak zarządzania focusem po zamknięciu modalu i brak aria-live przy większości komunikatów statusu.
  • Konfiguracja i deploy: brak proxy dev-serwera w vite.config.js (dev pod `vite --host 0.0.0.0` wymaga, by API leżało pod tym samym originem lub CORS), brak zmiennych środowiskowych dla API base — base path wykrywany heurystyką `pathname.includes('/panel')`, fonty ładowane z zewnętrznego CDN Google (zależność sieciowa i prywatnościowa), brak source-map/bundle-budgetu, brak PWA/offline i brak trybu 'API niedostępne' innego niż czerwony pasek błędu.
  • Backend eksponuje GET /api/audit (tylko admin), ale SystemPage jedynie informuje tekstem 'audit dostępny po wdrożeniu oddzielnego endpointu' i nigdy go nie woła — niedokończona funkcjonalność wprowadzająca operatora w błąd.
  • CSRF token trzymany w modułowej zmiennej w constants.js i ustawiany wyłącznie z /api/status: jeśli pierwszy request statusu padnie (a strony inne niż overview i tak się wyrenderują dzięki appContentGate), wszystkie mutacje polecą bez nagłówka i dostaną 403 bez czytelnej diagnozy dla użytkownika.
