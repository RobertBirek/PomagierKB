SUMMARY: optimaKB to workspace wdrożeniowy OpenSPG (platforma knowledge-graph: MySQL + Neo4j + MinIO + Tika + serwer Java) rozbudowany o trzy własne warstwy: pipeline eksportu/budowy KB (Node.js ESM, ~133 skrypty w scripts/ + 37 w scripts/lib/), warstwę asystenta/MCP odpowiadającą na pytania o Comarch Optima ERP, oraz dashboard operacyjny React/Vite (src/, 12 stron + 20 komponentów shared). Deployment to jeden compose.yaml z 5 usługami, wszystkie obrazy pinowane po digeście SHA256, wszystkie z healthcheckami, mem_limit i kotwicą hardeningową x-security-defaults (no-new-privileges:true + cap_drop:[ALL] + minimalny cap_add per usługa). Na hoście publikowane są tylko dwa porty: Tika na 127.0.0.1:9998 i serwer OpenSPG na ${OPENSPG_BIND_ADDRESS:-127.0.0.1}:${OPENSPG_PORT:-8887}; MySQL/Neo4j/MinIO są dostępne wyłącznie w wewnętrznej sieci `spg`. Dane leżą w bind-mountach pod /docker/openspg/data/*, a nie w wolumenach nazwanych. Konfiguracja jest w całości w .env (28 zmiennych) z fail-fast `:?required` dla każdego sekretu — brak zmiennej wywala `docker compose config`, zamiast cicho degradować do roota. package.json nie ma frameworka testowego: `npm run check` to gigantyczny łańcuch `node --check` po ~50 plikach, `npm run lint` to ESLint 8 na scripts/ + src/, a testy to ~20 samodzielnych skryptów `node scripts/test_*.mjs` wyeksponowanych jako osobne skrypty npm. Repo przeszło cztery audyty (2026-05-12, 2026-06-10, 2026-07-18, 2026-07-30), z których każdy udokumentował ustalenia ORAZ status remediacji — to najcenniejsza część repo. Audyt majowy zamknął podstawy (sekrety z compose do .env, digest-pinning, healthchecki, bind na LAN zamiast 0.0.0.0, APOC `*`→`apoc.*`, dedykowany user MySQL openspg_app zamiast roota). Audyt czerwcowy (21 ustaleń, wszystkie zamknięte tego samego dnia) złapał fail-open auth w dashboardzie i w mostach MCP, injection `javascript:` przez sourceUrl, naruszenie Rules of Hooks, brak rate-limitingu, brak backupów i masywną duplikację kodu pipeline'u (8 build-skryptów to 95% klony). Audyt lipcowy KAG/MCP zmapował 13 KB, 260+ jobów buildera, 5 (potem 9) serwerów MCP i wskazał, że retrieval de facto nie idzie przez OpenSPG tylko przez lokalny skan CSV. Audyt z 30 lipca był metodologicznie najciekawszy: sześć równoległych torów + adwersaryjna weryfikacja "na ślepo" (S2), która OBALIŁA jedno własne ustalenie audytu (T3 przetestował CORS na złej usłudze). Znalazł klucze API w publicznej historii gita, żywą regresję hardeningu kontenerów wdrożoną na produkcji, brak jakiejkolwiek autoryzacji na porcie 8887 i cały KB (InsERT GT) działający produkcyjnie poza gitem. Kluczowe wnioski techniczne o samym OpenSPG: relacje ze skryptu schematu NIE materializują się w grafie (workaround: właściwości refId), `builder/job/list` musi mieć `start=1` bo `start=0` wywala backendowy SQL, duże definicje SQL (>8192 tokenów) zabijają wektoryzację, a opublikowana aplikacja OpenSPG (app id=2) jest trwale niesprawna przez backendowy bug `projectId=2`.

  • MODELE — embedding text-embedding-3-small (OpenAI, model ID b87d551d4ba14909907c6e29218fa011); vector store to Neo4j przez właściwości TextAndVector; indeksy Text na name/sqlName/fieldName, TextAndVector na content/description/summary/definitionPreview/queryDesignNote.
  • ŚCIEŻKA INGESTII — datasource API tej instancji wspiera tylko ODPS i SLS (brak konektora MSSQL), więc praktyczna droga to: MSSQL export via Codex MCP → CSV → structured_builder_chain. Eksportowane są WYŁĄCZNIE metadane katalogu SQL Server, nigdy wiersze biznesowe.
  • SKALA DANYCH (LOCAL_KNOWLEDGE.md) — schema KB: 634 tabele, 12 426 kolumn, 609 FK, 1367 procedur, 743 funkcje, 449 triggerów, 11 702 parametry, 14 113 zależności obiektów, 13 118 chunków dokumentacji; PartnerTechnical: msg_entry.csv 21 140 wierszy, cfg_entry 5149, partner_asset 548; AdditionalFunctions: message_catalog_entry 7061.
  • GOTCHY OPERACYJNE — tabela Wydruki ma nieunikalne Wdr_ID (trzeba composite semantic id); krótkie keywordy jak `com` muszą być dopasowywane jako bounded tokens, inaczej marka `Comarch` fałszywie triggeruje ComarchOptimaAdditionalFunctions; assety partnerskie za Comarch SSO zwracają AUTH_REDIRECT_HTML gdy jest tylko PHPSESSID (potrzebne pełne ciasteczko przeglądarki); artefakty mutowane przez dashboard muszą pozostać zapisywalne dla użytkownika mcpbot po naprawach z roota.
  • CRON/AUTOMATYZACJA — 5 wrapperów shell wołanych przez crontab/systemd spoza repo: cron_autoheal_quality_gate.sh, cron_optima_schema_drift.sh, cron_refresh_comarch_community_news.sh, cron_refresh_taxbell_reference_sources.sh, cron_scan_dashboard_sources.sh. Zewnętrzne schedulery zależą od ich CLI i ścieżek wyjściowych — kontrakt trzeba sprawdzić przed zmianą.

REUSABLE:
  • Fail-fast na konfiguracji: KAŻDY sekret w compose to `${VAR:?VAR is required}`, nigdy `${VAR:-default}`. Audyt czerwcowy wprost złapał `${MYSQL_APP_USER:-root}` jako podatność — cicha degradacja do roota. W nowym projekcie: zero fallbacków dla czegokolwiek związanego z tożsamością/uprawnieniami.
  • Kotwica YAML `x-security-defaults: &security_defaults` z `no-new-privileges:true` + `cap_drop:[ALL]`, dziedziczona przez `<<: *security_defaults`, plus minimalny `cap_add` per usługa wyznaczony EMPIRYCZNIE z logów startu. Konkretne wartości do skopiowania: mysql [SETUID,SETGID], neo4j [CHOWN,DAC_OVERRIDE,FOWNER,SETUID,SETGID], reszta zero.
  • Pinowanie obrazów po digeście sha256 z komentarzem inline zawierającym ludzko czytelną wersję i datę builda — bez tego nikt nie wie, jak stary jest obraz. Pinuj też obrazy 'zewnętrzne' (apache/tika) — mutowalny tag `latest` był tu co noc podmieniany przez Watchtower.
  • Deny-by-default w bramkach uprawnień: `context.writeAllowed !== true` zamiast `=== false`. F-02 to podręcznikowy przykład, jak sprawdzanie negatywne przepuszcza `undefined`. Ta sama zasada dla auth: brak skonfigurowanych poświadczeń → 503, nigdy → rola admin.
  • Wymuszanie auth w zależności od bindu: REQUIRE_AUTH_ON_PUBLIC_BIND — twardy błąd startu, jeśli usługa binduje się poza 127.0.0.1 bez skonfigurowanego tokenu. Chroni przed dryfem konfiguracji, który wystawia otwartą usługę na LAN.
  • Rozdzielenie tokenów read/write w mostach MCP + stałoczasowe porównanie (timingSafeEqual/secureCredentialMatch) wyniesione do wspólnego lib/ i użyte w OBU mostach — fork Betterfly zgubił podział tokenów i to był finding High.
  • Audit log JSONL z redakcją sekretów + hash-chain (previousHash łączy zdarzenia) + retencja per-plik-dzienny (nie per-linia, bo to złamałoby łańcuch). Wzorzec z lib/dashboard_audit.mjs.
  • Jeden sparametryzowany runner + config per KB zamiast N sklonowanych skryptów. Wzorzec Taxbell (1 skrypt + taxbell_reference_config.mjs + 3-liniowe shimy env) został potem uogólniony na build_kb_runner.mjs z 10 profilami — to usunęło 8 klonów po 95% identycznych.
  • Centralny lib/config.mjs z domyślnymi endpointami — zanim powstał, adres `http://10.10.254.42:8887` był zaszyty jako fallback w 18 skryptach, czyli 18 miejsc do pomyłki przy migracji.
  • makeId z hashem zamiast ślepego obcinania: gdy slug przekracza limit długości, doklej 8-znakowy SHA1 PEŁNEJ wartości zachowując maksymalną długość. Ślepe `.slice(0, N)` zniszczyło unikalność ID w 8 z 13 KB — i wyglądało to jak 'duplikaty', a było utratą danych.
  • Atomowe zapisy plików (lib/atomic_file.mjs) + file-locki per KB dla read-modify-write manifestów. Dwa równoległe buildy korumpowały manifest JSON, zanim to dodano.
  • Guard SSRF (lib/safe_http.mjs) walidujący prywatne IPv4/IPv6, localhost, DNS-to-private, z RE-walidacją każdego przekierowania, plus allowlisty domen i namespace'ów — audyt wskazał go jako wzorcowy.
  • Warstwa write-side jako 'inbox draftów': narzędzie MCP submit_knowledge_draft pisze WYŁĄCZNIE lokalne pliki do downloads/knowledge_inbox/, nigdy nie mutuje grafu. Promocja do KB idzie normalną ścieżką export/build. To dramatycznie ogranicza blast radius kompromitacji MCP (audyt wprost obniżył severity F-02 z Critical na High z tego powodu).
  • Pamięć operacyjna jako plik: docs/reference/OpenSPG_KB_Operational_Memory.md — ręcznie utrzymywany, trwały zapis POTWIERDZONYCH zachowań API i stanu KB, czytany przez każdego agenta przed pracą. Oddzielony od raportów generowanych (te mają parę .md + .json i regeneruje je skrypt, nie człowiek).
  • Adwersaryjna weryfikacja audytu: po syntezie ustaleń uruchom niezależny przebieg, który próbuje odtworzyć każde twierdzenie OD ZERA, bez dostępu do oryginalnych dowodów. W audycie z 30 lipca to OBALIŁO własne ustalenie audytu (przetestowano CORS na złej usłudze) i doprecyzowało severity dwóch innych.
  • Tabela mapowania do poprzednich audytów w każdym nowym audycie: ustalenie → data → status wtedy → status dziś → dowód. Bez tego regresje (jak F-08, odwrócenie zamkniętego ustalenia z czerwca) są niewidoczne.
  • Rozróżnianie w raportach POTWIERDZONE / WNIOSKOWANE / HIPOTEZA oraz jawna tabela 'co sprawdzono live komendą, co odczytano z raportu, czego nie zweryfikowano'. Audyt lipcowy trafnie oznaczył 'job FINISH ≠ dowód że 133 wiersze są węzłami grafu'.
  • Statusy remediacji wpisywane BEZPOŚREDNIO w dokument audytu (WDROŻONE data / NIE WDROŻONO / wymaga zgody użytkownika / ODŁOŻONE z uzasadnieniem) — dokument audytu jest żywym trackerem, nie zamrożonym snapshotem.
  • Preflight jako osobny, ostrzejszy skrypt niż smoke test: preflight_erp_knowledge_mcp_http_bridge.mjs sprawdza pliki, startuje most lokalnie, wywołuje /health + tools/list + realne answer_question i kończy maszynowo czytelnym JSON-em pass/fail.
  • Strukturalny JSON na stdout we wszystkich skryptach CLI (przyjazne cronowi) + exit code != 0 przy porażce — to pozwala traktować pojedyncze skrypty Node jako testy bez frameworka.
  • Zewnętrzne integracje przez EXA/Exa search jako fallback przy niskim confidence + rejestrowanie 'learning gaps' (lib/learning.mjs) — system zapisuje, czego nie wiedział, zamiast po prostu zwrócić słabą odpowiedź.

WEAKNESSES:
  • Brak jakiegokolwiek test runnera. `npm run check` to łańcuch ~50 wywołań `node --check` w JEDNEJ linii JSON-a — waliduje wyłącznie składnię i nie łapie nic semantycznego (F-06: test hardkodujący 6 profili przy 7 w kodzie przechodził `check` na zielono). W nowym projekcie: vitest/node:test od pierwszego dnia, jeden `npm test`, CI.
  • Testy jako ~20 niezależnych skryptów npm bez wspólnego runnera oznacza, że nikt nie uruchamia wszystkich naraz — dwa z nich (test_erp_knowledge_mcp_protocol.mjs, test_erp_knowledge_mcp_http_bridge_write_access.mjs) były trwale niekompatybilne z wdrożonym Node 18 przez import.meta.dirname i nikt tego nie zauważył do audytu.
  • Brak CI/CD w ogóle. Cały pipeline budowy jest manualny/skryptowy, wdrożenia idą przez ręczne `docker compose up -d`, testy nie są bramką na merge. Skutek: kod na produkcji rozjeżdżał się z gitem (F-07: cały KB InsERT GT — 4 skrypty + schema — działał produkcyjnie z systemd, a `git log` na tych plikach był PUSTY).
  • Brak środowiska dev/staging — jedno środowisko produkcyjne na 10.10.254.42. Audyt nie mógł zreprodukować buga app=2, bo wymagałoby to akcji stanotwórczej na produkcji.
  • Sekrety w plaintext w śledzonym pliku w PUBLICZNYM repo (F-01, opencode.json, commit a66d69e w historii origin/main). Wzorzec provider_secrets.mjs istniał w tym samym repo i nie został użyty. W nowym projekcie: sekrety nigdy w plikach konfiguracyjnych narzędzi, skanowanie pre-commit (gitleaks/trufflehog), publiczność repo jako świadoma decyzja z audytem historii.
  • Sekrety wciąż w .env, nie w Docker Secrets ani vaulcie — i dodatkowo OpenSPG WYMAGA sekretów inline w connection URL-ach (CLOUDEXT_*), więc są widoczne przez `docker inspect` i /proc/<pid>/environ dla każdego z dostępem do dockera. Jedyna mitygacja to ograniczenie grupy `docker`. Konieczność utrzymywania osobnych zmiennych *_URLENCODED to objaw tego samego długu.
  • Brak jakiejkolwiek autoryzacji na API OpenSPG (port 8887) — builder job list i root zwracają 200 z danymi bez Authorization, dostępne z całego LAN (F-22). CORS odbija dowolny Origin z Allow-Credentials:true i jest zaszyty w kodzie Javy upstreamu (brak właściwości cors w application-*.properties, brak zamontowanego configa). Naprawa wymaga postawienia reverse-proxy, którego dziś nie ma. To najstarsze otwarte ustalenie — od maja.
  • Bindowanie usług na adres LAN, nie na 127.0.0.1 + proxy. Reguła ufw nie działa, bo Docker robi DNAT z 0.0.0.0/0 zanim ufw dostanie szansę filtrować — właściwe miejsce to łańcuch DOCKER-USER. W nowym projekcie: wszystko na loopback + jeden świadomy punkt wejścia z TLS i auth.
  • Bind-mounty na absolutne ścieżki hosta (/docker/openspg/data/...) zamiast wolumenów nazwanych — wiąże compose z konkretną maszyną i utrudnia przeniesienie/testy.
  • Regresje wdrażane na produkcję bez commita: F-08 (usunięcie hardeningu z 5 kontenerów) było w working tree i ŻYWE na kontenerach, potwierdzone przez docker inspect i docker compose config --hash. Brak drift detection między stanem gita a stanem runtime.
  • Automatyzacja z jednokierunkowym zatrzaskiem: health-check ustawia paused:true przy 2 błędach, ale ŻADNA ścieżka nie ustawia paused:false przy powrocie do zdrowia — canary stało wstrzymane 8 dni mimo przechodzącego dziś health-checka. Każdy circuit breaker potrzebuje ścieżki auto-recovery (np. po N kolejnych sukcesach) albo przynajmniej alertu.
  • Skrypty w pętli 100% CPU bez watchdoga: check_dashboard_llm_health.mjs jadł 3100 CPU-minut przez 2 dni, a unit systemd wisiał w `activating`, blokując wszystkie kolejne przebiegi timera. Brakowało TimeoutStartSec i twardego limitu w samym skrypcie.
  • Procesy produkcyjne uruchamiane ręcznie jako root poza systemd (Betterfly MCP bridge, mssql-mcp-server z cache npx) — brak auto-restartu, sandboxingu i audytu.
  • Masywna duplikacja przez copy-paste jako domyślny sposób dodawania KB: 8 build-skryptów w 95% identycznych, 9 eksporterów z DRYFEM helperów (regex slug() różny, cap długości id 96 vs 110) — to bezpośrednio wyprodukowało niespójne identyfikatory encji między KB. Nowy projekt musi mieć jeden runner + deklaratywne configi od początku.
  • Dokumentacja utrzymywana ręcznie i rozjeżdżająca się ze stanem: tabela KB w AGENTS.md miała 7 z 14 baz (F-11), §14 AUDIT_OPENSPG_KAG_MCP.md miała 5 serwerów MCP zamiast 9 (F-05), operational memory twierdziła 'workflow_pattern.csv: 0' gdy było 133 wiersze. Wszystko, co da się wygenerować z rejestru, trzeba generować, a nie kopiować.
  • 80+ plików Markdown w docs/reference/ z mieszaniną dokumentacji narracyjnej i maszynowego store'u stanu (pary .md + .json) — bez konwencji nazewniczej jednoznacznie odróżniającej generowane od ręcznych. LOCAL_KNOWLEDGE.md to 604 linie płaskiej listy plików z linkami do absolutnych ścieżek /docker/openspg/.
  • Brak kanonicznej ontologii ERP: ReferenceDocument istnieje niezależnie w 7+ KB z różnymi zestawami właściwości, Chunk w 7+ KB z drobnymi różnicami, SchemaTouchpoint vs ComSchemaTouchpoint to ten sam koncept pod dwoma nazwami. Model nie odróżnia BusinessConcept/Process/ProcessStep/BusinessRule/Capability/ApiOperation/ErrorCode.
  • Relacje modelowane jako właściwości refId, bo OpenSPG nie materializuje niestandardowych linii relacji — czyli graf jest de facto zbiorem tabel z kluczami obcymi, bez multi-hop reasoning i bez wnioskowania symbolicznego. Procesy biznesowe istnieją tylko jako dokumentacja, nie jako operacyjny graf reguł.
  • Retrieval nie idzie przez KAG/OpenSPG, tylko przez synchroniczny skan CSV przy każdym żądaniu (erp_knowledge_answer.mjs czyta całe pliki) — wzmacniacz latencji/DoS przy rosnących eksportach, brak cache z inwalidacją po mtime. Benchmark 200/200 PASS mierzy TYLKO routing, nie jakość odpowiedzi.
  • Brak multi-tenancy: potwierdzone (nie wnioskowane) że w kodzie nie ma pojęcia tenanta — izolacja jest per-proces/port i per-projekt Neo4j, nie per-request. Pojedynczy bearer token daje dostęp do wszystkich KB, chyba że ręcznie skonfigurowano ALLOWED_NAMESPACES na osobnej instancji.
  • Brak wersjonowania faktów: żadnego validFrom/validTo, sourceVersion, verifiedAt, ani mechanizmu rozwiązywania konfliktów między źródłami. Provenance częściowe (sourceUrl/sourceOrigin), source_registry.json tylko dla Betterfly i Partner.
  • Brak dedup po URL w warstwie download/snapshot — ten sam URL jest snapshotowany wielokrotnie w różnym czasie, produkując zduplikowane chunki w wielu KB (F-19 root cause #2, nienaprawiony).
  • Zmiana schematu ID bez ścieżki migracji: naprawa makeId oznacza, że rebuild stworzy nowe węzły OBOK starych zamiast je nadpisać. Brak w ogóle strategii migracji/wersjonowania danych w grafie.
